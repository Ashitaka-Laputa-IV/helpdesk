# RAG 程序首字响应时间（TTFT）报告

## 1. 指标定义

**首字响应时间（TTFT）**：从发起请求到用户看到第一个字的时间。

刻意不计入整段生成时间——那由回答长度决定（同一流程可从 0.4s 到 9s），
衡量不出"响应快不快"。本报告只回答一个问题：**用户等多久才见到第一个字**。

但只看速度会得出"不排序最快"的错误结论，所以第 3.4 节同时给出各方案的
**检索质量（Recall@8 / MRR）**，两者合起来才构成选型依据。

## 2. 测试方法

脚本：`tests/benchmark_ttft.py`

```bash
uv run python tests/benchmark_ttft.py --repeat 10
```

| 项 | 设置 |
|---|---|
| 被测方案 | 无排序 / rerank / RRF / Agentic |
| 问题 | 2 个必检索的英文问题（定义工具、向量检索流程） |
| 轮数 | 10 轮 × 2 问 = **每方案 20 个样本** |
| 顺序 | 每轮轮转方案顺序，抵消先后偏差 |
| 预热 | 正式计时前先跑一次，排除建连与模型加载 |
| 计时 | `graph.stream(stream_mode="messages")`，**只认 `chatbot`/`model` 节点**的首个有内容 token |
| 结束 | 取到首字立即关闭流，不等待生成完成 |
| 隔离 | 每个样本使用独立 `thread_id`，无历史干扰 |

环境：`qwen3-4b-instruct` @ 9938、`bge-m3` @ 9931、`bge-reranker-v2-m3` @ 9932；
语料 180 篇英文文档，召回 `bm25_k=25` + `sem_k=15`，RRF `k=20`，进入上下文 8 条。

## 3. 结果

### 3.1 汇总（每方案 20 样本）

| 方案 | 平均 | 中位 | P95 | 最快 | 最慢 |
|---|---|---|---|---|---|
| **RRF** | **541ms** | **520ms** | **641ms** | 461ms | 641ms |
| 无排序 | 575ms | 579ms | 659ms | 473ms | 659ms |
| rerank | 1520ms | 1523ms | 1787ms | 1226ms | 1787ms |
| Agentic | 2006ms | 1826ms | 2338ms | 1700ms | 2338ms |

### 3.2 分问题（中位）

| 方案 | Q1 定义工具 | Q2 检索流程 |
|---|---|---|
| RRF | 517ms | 534ms |
| 无排序 | 579ms | 597ms |
| rerank | 1479ms | 1604ms |
| Agentic | 1781ms | 2056ms |

两个问题的排序完全一致，说明结论不受单个问题影响。

### 3.3 相对 RRF 的增量

| 方案 | 平均 TTFT | 相对 RRF | 倍数 |
|---|---|---|---|
| RRF | 541ms | — | 1.0× |
| 无排序 | 575ms | +34ms | 1.1× |
| rerank | 1520ms | **+979ms** | 2.8× |
| Agentic | 2006ms | **+1465ms** | 3.7× |

### 3.4 质量与响应合并视图

只看首字会得出"不排序最快"，但那是牺牲质量的快。因此把检索质量并进来一起看。

召回质量取自 `tests/compare_ranking.py`（30 条英文改写问题，同一召回池，文档级去重，`top_n=8` 为生产配置）。

**改写档（用户口语提问，主场景）**

| 方案 | Recall@8 | MRR | 首字中位 | 首字 P95 | 排序开销 |
|---|---|---|---|---|---|
| **RRF** | **90.0%** | **0.723** | **520ms** | **641ms** | 0.02ms |
| 无排序 | 83.3% | 0.568 | 579ms | 659ms | 0 |
| rerank | 86.7% | 0.704 | 1523ms | 1787ms | 800ms |

**标题档（直接搜术语，字面重合多）**

| 方案 | Recall@8 | MRR |
|---|---|---|
| RRF | 100% | 0.762 |
| 无排序 | 100% | 0.651 |
| rerank | 100% | **0.940** |

> Agentic 内部走同一套 RRF 召回（融合在检索工具里完成），召回质量与 RRF 同级；
> 它与其他三者的差别在"要不要检索、检索几次"的判断，而非排序方式。

**帕累托视角**：

- **RRF 同时拿下三项第一**（改写档召回 90.0%、MRR 0.723、首字 520ms），是明确的帕累托最优点；
- 无排序唯一胜出的指标是"省掉 0.02ms 融合"，代价是召回掉 6.7 个点、MRR 掉 0.155；
- rerank 只在**标题档的 MRR**（0.940）上领先，但要多等 1 秒，改写档召回还低于 RRF。

## 4. 分析

### 4.1 时间花在哪

以无排序（575ms）为基线：

| 环节 | 估算 | 说明 |
|---|---|---|
| router 判是否检索 | 约 400~450ms | 一次结构化输出调用，`max_tokens=128` |
| 召回（bm25 + 向量） | 约 15ms | bm25 0.5ms，向量约 14ms |
| 排序 | 0 / 0.02ms / 800ms | 无排序 / RRF / rerank |
| 首 token 生成 | 约 100ms | 首字前的 prefill |

- **rerank 多出的 979ms** 与它 800ms 的重排开销基本吻合，剩余来自更长的上下文带来的 prefill 增加。
- **Agentic 多出的 1465ms** 来自"先让模型决定要不要用工具"这一整轮调用——在首字之前又插了一次完整的模型往返。

### 4.2 稳定性

| 方案 | 波动区间（最快~最慢） | 极差 |
|---|---|---|
| RRF | 461~641ms | 180ms |
| 无排序 | 473~659ms | 186ms |
| rerank | 1226~1787ms | 561ms |
| Agentic | 1700~2338ms | 638ms |

RRF 与无排序的波动都控制在 200ms 内，重排与 Agentic 的极差是它们的 3 倍以上——
不仅更慢，也**更不可预测**。

### 4.3 为什么 RRF 比"无排序"还快一点

两者只差一次融合计算（0.02ms），34ms 的差额属测量噪声，不应解读为"融合更快"。
可以确认的是：**RRF 的融合成本在首字维度上不可感知**。

## 5. 结论

1. **RRF 在质量与速度上同时最优**：首字中位 520ms（最快），
   改写档 Recall@8 **90.0%**、MRR **0.723**（均最高）。
   它能做到"比不排序还快、且召回高 6.7 个点"，是因为融合只花 0.02ms。
   **没有理由为了首字而放弃排序**。
2. **rerank 的代价是约 1 秒**：1520ms，是 RRF 的 2.8 倍。
   只有在"必须把最相关的那条排第一"时才值得（标题式查询 MRR 0.940）。
3. **Agentic 首字最差**：2006ms，比 RRF 多 1.5 秒。
   代价来自工具决策那一轮模型调用；它的价值在"自主改写查询/多次检索"，不在响应速度。
4. **响应速度与检索质量可以兼得**：RRF 同时拿到 520ms 的首字和 90% 的召回，
   是当前配置下的默认选择。

## 6. 复现

```bash
# 首字响应时间（4 方案 × 10 轮 × 2 问）
uv run python tests/benchmark_ttft.py --repeat 10

# 检索质量（Recall/MRR）
uv run python tests/compare_ranking.py --repeat 2
```

## 7. 局限

- 仅 2 个问题，覆盖"必检索"场景；寒暄类（不检索）首字更快，未纳入。
- 单机本地模型服务，绝对毫秒数受硬件与负载影响；**相对关系**才是结论。
- 取到首字即断开流，因此不反映整段回答的完成时间（那需另测）。
- `qwen3-4b-instruct` 为 4B 模型，换用更大模型时 router/工具决策耗时会上升。
