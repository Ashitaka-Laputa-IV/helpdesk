# RAG 两种实现：固定编排 vs Agentic

## 目标

同一套语料、同一个模型，对比两条 RAG 路线：

| | 流程控制 | 构建函数 |
|---|---|---|
| **A** | 固定编排，router 节点决定是否检索 | `router_chat.build_graph(...)` |
| **B** | `create_agent` + 检索工具，模型自主决定 | `rag_agent.build_agent(...)` |

两者的检索链路完全一致：**bm25(10) + 语义(15) 去重 → rerank 取前 5**。
区别只在于「要不要检索」这一决策由谁做、以及流程是否写死。

## 实现差异

### A. 固定编排（`src/helpdesk/router_chat.py`）

```mermaid
graph TD
    Start([Start]) --> Summarize[summarize]
    Summarize --> Router{Router<br/>判是否检索}
    Router -- 检索 --> BM25[bm25 10]
    Router -- 检索 --> Semantic[semantic 15]
    Router -- 不检索 --> Chatbot
    BM25 --> Combine[去重合并] --> Rerank[rerank 取 5] --> Chatbot[chatbot]
    Chatbot --> END([END])
```

- 是否检索由 **router 节点**单独调一次模型判定（`with_structured_output` 返回 `retrieve/chatbot`）。
- 检索固定只做**一次**，字段 `context` 传给 chatbot。

### B. Agentic（`src/helpdesk/rag_agent.py`）

```mermaid
graph TD
    Start([Start]) --> Agent[agent<br/>create_agent]
    Agent -- 调用 search_knowledge_base --> Tool[检索工具<br/>bm25+语义 -> rerank]
    Tool --> Agent
    Agent -- 不调用 --> END([END])
```

- 只提供一个工具，**何时检索、检索几次、要不要换关键词再查**都由模型决定。
- 提示词承担了原来 router 的职责，是这条路线成败的关键：

```text
【什么时候调用工具 search_knowledge_base】
- 问题涉及 LangChain、LangGraph 的概念、API、类名、参数、配置方式时，先调用它，不要凭记忆作答。
- 一次检索结果不相关或信息不全时，换更准确的关键词再检索，最多 3 次。
- 寒暄、与文档无关的闲聊、或对话历史里已经给出过答案时，不要调用工具，直接回答。

【怎么回答】
- 只使用工具返回的资料和对话历史，不要补充资料之外的内容。
- 资料里没有的信息，直接说明「资料中没有提到」，不要编造。
- 用中文简洁回答，必要时给出代码片段，并标注来源文件名。
```

工具本身（bm25 与向量召回并发执行，与 A 的图上 fan-out 等价）：

```python
@tool
def search_knowledge_base(query: str) -> str:
    """在 LangChain / LangGraph 官方文档库中检索，返回最相关的几段原文。"""
    with ThreadPoolExecutor(max_workers=2) as pool:
        bm25_future = pool.submit(search, bm25, chunks, query, BM25_K)
        vector_future = pool.submit(retriever.invoke, query)
        bm25_hits = bm25_future.result()
        vector_docs = vector_future.result()
    # 去重 -> rerank 取前 5
```

## 测试

脚本：`tests/compare_rag.py`

```bash
uv run python tests/compare_rag.py
```

**串行**执行：A 跑完 6 轮，B 再跑一遍；各自独立的 `thread_id` 与内存 checkpointer。

### 语料（6 轮）

| 轮次 | 输入 | 期望检索 | 考察点 |
|---|---|---|---|
| 1 | 你好 | 否 | 寒暄不检索 |
| 2 | LangChain 里怎么定义一个工具？ | 是 | 需要查文档 |
| 3 | 向量库检索的基本流程是什么？ | 是 | 需要查文档 |
| 4 | 我刚才问过的技术问题是什么？ | 否 | 历史可回答 |
| 5 | 谢谢 | 否 | 致谢不检索 |
| 6 | LangChain 里怎么定义一个工具？（重复第 2 轮） | 否 | 历史已有答案 |

### 结果

**单次逐轮耗时**（毫秒，修正校验后的一次运行）

| 轮次 | A 固定编排 | B Agentic |
|---|---|---|
| 1 | 305 | 352 |
| 2 | 5489 | 6086 |
| 3 | 6417 | 6021 |
| 4 | 995 | 388 |
| 5 | 165 | 221 |
| 6 | 3228 | 3981 |
| **总计** | **16.60s** | **17.05s** |

**多次运行**（校验口径一致；B 后两行为并行召回版本）

| 运行 | 候选数 | A 总耗时 / 检索判定 | B 总耗时 / 检索判定 |
|---|---|---|---|
| 1 | 60（40+20） | 16.60s / 6-6 | 17.05s / 6-6 |
| 2 | 60（40+20） | 19.63s / 6-6 | 33.21s / 6-6 |
| 3 | 60（40+20，B 并行召回） | 18.84s / 6-6 | 17.62s / 6-6 |
| 4 | 60（40+20，B 并行召回） | 16.22s / 6-6 | 18.75s / 6-6 |
| 5 | 25（10+15） | 23.86s / **4-6** | 14.75s / 6-6 |
| 6 | 25（10+15） | 16.63s / 6-6 | 14.57s / 6-6 |

所有运行的答案关键词校验均为 6/6（含候选数降到 25 条之后，答案质量未见下降）。

### 召回环节微基准

端到端耗时被模型抖动淹没，单独测量工具内部的两个召回源（预热后取 8 次中位数）：

| 环节 | 耗时 |
|---|---|
| 仅 bm25（6700 块，本地索引） | **0.1ms** |
| 仅向量召回（HTTP → bge-m3） | 7.0ms |
| 串行两步 | 7.9ms |
| 并行两步 | 7.3ms |
| **并行相对串行** | **-6.5%（省 0.6ms）** |

再补测重排（候选数 = bm25 召回 + 向量召回去重后的条数）：

| 候选数 | rerank 耗时 |
|---|---|
| 60 条（bm25 40 + 语义 20） | 1335ms |
| 25 条（bm25 10 + 语义 15） | **586ms** |

结论很明确：

1. **召回链路 99% 的时间花在 rerank 上**。把 bm25 与向量召回改成并行，只能省 0.6ms（0.04%），
   对 5~7s 的一轮问答完全不可感知——这也解释了为什么并行前后端到端数据看不出差别。
2. **降低候选数才是有效手段**：60 → 25 条，rerank 从 1335ms 降到 586ms，单次检索省约 750ms。

## 结论

1. **检索决策能力等价**：两者都做到 6/6，寒暄、致谢、重复提问都能正确跳过检索。
2. **耗时无法区分**：候选数 60 时，A 16.60 / 19.63 / 18.84 / 16.22s，B 17.05 / 33.21 / 17.62 / 18.75s。
   B 的 33.21s 是服务抖动（同一轮 6.1s → 10.9s），不代表实现差异；轮次粒度上两者交替领先。
   候选数降到 25 后，B 稳定在 14.57 / 14.75s（每轮少约 750ms 的 rerank），A 仍受 router 与生成抖动影响（16.63 / 23.86s）。
3. **A 出现过一次误判**：在某次运行中，第 4 轮「我刚才问过的技术问题是什么？」
   被 router 判成需要检索（5/6）。B 在全部运行中该轮都直接回答，未触发检索。
   原因推测：A 的 router 只看压缩后的历史摘要 + 最近若干条，B 的 agent 直接看完整 messages 自行判断。
   仅一次观察，不足以定论，但方向与上一轮「对话形态更适合判断重复提问」的结论一致。
4. **可控性与成本**：
   - A 多一次 router 模型调用（固定开销），但流程确定、易调试、行为可预测；
   - B 省掉这次调用，但行为依赖提示词，检索次数与时机不固定，排障要看工具调用轨迹。
5. **性能瓶颈在 rerank，不在召回**：并行化 bm25/向量只省 0.6ms（0.04%）；
   把候选从 60 降到 25 后 rerank 从 1335ms 降到 586ms，单次检索省约 750ms，且答案质量未下降。
   继续提速的选项：再减小候选数、换更小的 reranker、或缩短 chunk 长度（当前 1000 字）。

## 选择建议

- 若问题形态稳定、要求行为可预测（客服常见场景）→ **A 固定编排**。
- 若问题类型差异大、需要多轮改写检索或按需多次查证 → **B Agentic**。
- 两者检索链路相同，可以先上 A 保底，再用 B 处理复杂问题（路由分发）。
