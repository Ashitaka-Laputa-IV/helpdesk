# 向量索引重复检查

## 背景

怀疑 `.chroma` 里的分块被重复插入：`build_rag` 用 `add_documents` 写入且未指定 id，
Chroma 会自行生成 UUID，若索引过程跑过两遍，同一段内容就会以多个不同 id 存在。

本次检查回答三个问题：

1. 索引里是否被重复插入？
2. 如果没有，为什么分块数和唯一内容数不一致？
3. 这些重复会不会影响检索效果？

## 检查方法

### 第一步：索引数量 vs 单次切分数量

```python
from langchain_chroma import Chroma
from langchain_text_splitters import RecursiveCharacterTextSplitter
from taste_rag.corpus import DOCS_DIR
from taste_rag.vector_store import COLLECTION, INDEX_DIR, load_documents

store = Chroma(collection_name=COLLECTION, embedding_function=embeddings,
               persist_directory=str(INDEX_DIR))
data = store.get(include=["documents", "metadatas"])

splits = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200) \
    .split_documents(load_documents(DOCS_DIR))
```

若索引被插入两遍，总数应约为单次切分的 2 倍。

### 第二步：内容层面的重复统计

- 唯一文本数：`len(set(documents))`
- 唯一(来源, 文本)对数：`len({(metadata["source"], text)})`
  —— 区分「同文档内重复」与「跨文档重复」

### 第三步：重复对检索的实际影响

对评测集（`data/eval/queries.json` 的 30 条英文改写查询）逐条：

1. 走 bm25(10) + 向量(15) 得到候选池
2. 统计候选池里「唯一文本数 / 总条数」
3. 重排取 top-5，统计唯一文本占比，并检查是否出现内容重复

## 结果

### 1. 索引没有被重复插入

| 指标 | 数值 |
|---|---|
| 索引分块总数 | **7008** |
| 单次切分应产生 | **7008** |
| 唯一文本数 | 5708 |
| 唯一(来源, 文本)对数 | 6924 |

总数与单次切分完全一致，说明索引只写入了一遍。

### 2. 内容重复来自语料本身

| 类型 | 数量 | 说明 |
|---|---|---|
| 跨文档重复 | 7008 - 5708 = **1300 块** | 同一段内容出现在多个文档里 |
| 同文档内重复 | 7008 - 6924 = **84 块** | 同一文件里有完全相同的片段 |
| 重复率 | 约 **18%** | 1300 / 7008 |

重复最多的片段（原样出现 17 次）：

```
export const PatternEmbed = ({pattern, i...
enum: _values => stub(),
    array: _el ...
});
  var ResetMessageSchema = z.object(...
```

这类内容是前端示例代码，被复制到了多个页面。

### 3. 对检索几乎没有影响

| 指标 | 结果 |
|---|---|
| 候选池平均唯一文本占比 | 97.5% |
| rerank top-5 平均唯一文本占比 | **100.0%** |
| top-5 出现内容重复的查询 | **0 / 30** |

重复片段处在检索长尾，很少被这些查询命中，没有挤占 top-k 名额。

> 注：`data/langchain-docs` 共 180 篇文档；bm25 用的是自己的切分（6700 块），
> 与 Chroma 的 7008 块口径不同，但内容来源相同，重复情况一致。

## 结论

1. **不是 bug**：索引没有重复写入，数量与单次切分吻合。
2. **重复率约 18%**，源于语料本身（示例代码被多页复用），不是索引流程问题。
3. **对当前检索无实质影响**：候选池唯一率 97.5%，top-5 唯一率 100%，0/30 命中重复。
4. **可选优化**：建索引时按内容去重，可省约 1300 次嵌入和 18% 索引体积，
   对检索效果无影响。代价是需要重建索引（约 6 分钟）。
