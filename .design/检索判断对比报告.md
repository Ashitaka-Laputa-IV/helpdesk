# 检索判断对比报告：有判断 vs 总是检索

## 1. 目的

RAG 流程里"要不要检索"这一步值不值得做？

- **有判断**：先让模型判断问题是否需要查文档，不需要就直接回答
- **总是检索**：跳过判断，一律检索后再回答

两者使用**完全相同的检索链路**（bm25 25 + 向量 15 → RRF k=20 → top 8），
只差这一个决策环节，因此差异全部来自"是否检索"。

## 2. 测试方法

脚本：`tests/compare_router_decision.py`

```bash
uv run python tests/compare_router_decision.py --repeat 6 --token-repeat 4
```

| 项 | 设置 |
|---|---|
| 变异点 | `router_mode`：`llm`（判断） vs `always`（总是检索） |
| 问题 | 4 个：寒暄、必检索、历史追问、致谢 |
| 首字样本 | 6 轮 × 4 问 = 每方案 24 个 |
| Token 样本 | 4 轮 × 4 问 = 每方案 16 个 |
| 首字测量 | `stream` 取到首字即关闭流，只认 `chatbot` 节点 token |
| Token 测量 | 非流式 `invoke` + callback 统计，覆盖 router 与 chatbot 全部调用 |
| 隔离 | 每个样本独立 `thread_id`；正式测量前预热一次 |

> 本地服务流式不返回 usage，故首字与 token 分两阶段测量。

## 3. 结果

### 3.1 汇总

| 方案 | 首字中位 | 首字 P95 | 输入均值 | 输入中位 | 输出均值 | LLM 调用/轮 | 检索比例 |
|---|---|---|---|---|---|---|---|
| **有判断** | **233ms** | 514ms | **972** | **957** | 84 | 1.5 | 8/16 |
| 总是检索 | 266ms | **424ms** | 2453 | 1817 | 72 | 1.0 | 16/16 |

### 3.2 分问题（首字中位 / 输入 token 均值）

| 问题 | 期望检索 | 有判断 | 总是检索 |
|---|---|---|---|
| `Hello` | 否 | **32ms / 25** | 401ms / 1455 |
| `How do I define a tool in LangChain?` | 是 | 322ms / 1949 | **196ms / 1846** |
| `What technical question did I just ask?` | 否 | 477ms / 1889 | **254ms / 1788** |
| `Thanks` | 否 | **143ms / 25** | 303ms / **4723** |

## 4. 分析

### 4.1 Token 消耗：判断能省一半以上

| 指标 | 有判断 | 总是检索 | 差异 |
|---|---|---|---|
| 输入均值 | 972 | 2453 | **-60.4%** |
| 输入中位 | 957 | 1817 | -47.3% |
| 输出均值 | 84 | 72 | 基本持平 |

差异几乎全在**输入侧**：省掉的是"检索到的 8 段资料"及其拼装。
输出 token 两者接近，说明回答长度不受影响。

极端例子：`Thanks` 在"总是检索"下输入 **4723 token**——为一句致谢检索了 8 段长文档，
是有判断方案（25 token）的 189 倍。

### 4.2 首字延迟：判断更快，但尾部更差

- **中位 233ms vs 266ms**：判断更快，因为两个寒暄/致谢问题直接跳过检索（32ms、143ms）。
- **P95 514ms vs 424ms**：判断的尾部更差，原因是它**会误判**。
  本次测试中 `What technical question did I just ask?` 四轮全部被判成需要检索，
  首字 477ms、输入 1889 token——本该秒回的问题付出了完整检索代价。

### 4.3 调用次数：判断要多付一次往返

| 方案 | LLM 调用/轮 |
|---|---|
| 有判断 | **1.5** |
| 总是检索 | 1.0 |

判断方案在非寒暄问题上多一次 router 调用（`max_tokens=128`），
反映在必检索问题上：322ms vs 196ms，**慢约 126ms**。这是判断的固定成本。

### 4.4 两种失败模式的代价对比

| 失败 | 后果 |
|---|---|
| 有判断 **误判为需检索**（本次历史问题 4/4） | 多 1899 token、首字 477ms（正常应 ~100ms） |
| 总是检索 **不该查却查了**（寒暄/致谢） | 多 1430~4698 token、首字 303~401ms |

两者方向一致：多查一次的代价约为 1.5~4.7k token 与 200~400ms 首字。

## 5. 结论

1. **判断环节值得保留**：输入 token 均值降 **60%**，首字中位快 33ms，代价仅 0.5 次调用/轮。
2. **收益集中在"非知识型问题"**：寒暄、致谢类问题省下 1.4k~4.7k token，首字快 300ms 以上。
3. **必检索问题会因判断而略慢**（+126ms）：这是一次固定开销，可接受。
4. **真正的风险是误判**：本次历史追问 4/4 被误判为需检索，把"该秒回"变成"完整检索"。
   因此优化重点不是去掉判断，而是**提高判断准确率**（换更强的 router 模型 / 补规则）。
5. **若判断不可靠，宁可总是检索**：多花 token 但不漏查，质量优先于成本时可接受。

## 6. 复现

```bash
uv run python tests/compare_router_decision.py --repeat 6 --token-repeat 4
```

## 7. 局限

- 仅 4 个问题，覆盖寒暄/必检索/历史/致谢各一，样本小，方向性结论为主。
- 单机本地服务，token 与延迟绝对值受硬件影响，看相对差异。
- 首字与 token 分两阶段测量（流式无 usage），两者不是同一次运行的样本。
- 输入 token 方差大（受检索到的文档长度影响），故同时给出均值与中位。
