# 检索判断对比报告：有判断 vs 总是检索

## 1. 目的

RAG 流程里"要不要检索"这一步值不值得做？

- **有判断**：先让模型判断问题是否需要查文档，不需要就直接回答
- **总是检索**：跳过判断，一律检索后再回答

两者使用**完全相同的检索链路**（bm25 25 + 向量 15 → RRF k=20 → top 8），
只差这一个决策环节，因此差异全部来自"是否检索"。

> **版本说明**：本报告数据在**移除寒暄/致谢正则快路径之后**采集。
> 早前版本用正则把 `Hello`/`Thanks` 直接判为不检索（32ms/143ms），
> 相当于给"有判断"方案开了后门；现在寒暄与业务问题一视同仁，都走模型判断。

## 2. 测试方法

脚本：`tests/compare_router_decision.py`

```bash
uv run python tests/compare_router_decision.py --repeat 6 --token-repeat 4
```

| 项 | 设置 |
|---|---|
| 变异点 | `router_mode`：`llm`（判断） vs `always`（总是检索） |
| 问题 | 4 个：寒暄、必检索、历史追问、致谢 |
| 首字样本 | 6 轮 × 4 问 = 每方案 24 个 |
| Token 样本 | 4 轮 × 4 问 = 每方案 16 个 |
| 首字测量 | `stream` 取到首字即关闭流，只认 `chatbot` 节点 token |
| Token 测量 | 非流式 `invoke` + callback 统计，覆盖 router 与 chatbot 全部调用 |
| 隔离 | 每个样本独立 `thread_id`；正式测量前预热一次 |

> 本地服务流式不返回 usage，故首字与 token 分两阶段测量。

## 3. 结果

### 3.1 汇总

| 方案 | 首字中位 | 首字 P95 | 输入均值 | 输入中位 | 输出均值 | LLM 调用/轮 | 检索比例 |
|---|---|---|---|---|---|---|---|
| 有判断 | 357ms | 500ms | **1019** | **1004** | 80 | 2.0 | 8/16 |
| **总是检索** | **259ms** | **400ms** | 2453 | 1817 | 79 | 1.0 | 16/16 |

### 3.2 分问题（首字中位 / 输入 token 均值）

| 问题 | 期望检索 | 有判断 | 总是检索 |
|---|---|---|---|
| `Hello` | 否 | **263ms / 119** | 360ms / 1455 |
| `How do I define a tool in LangChain?` | 是 | 316ms / 1949 | **193ms / 1846** |
| `What technical question did I just ask?` | 否 | 474ms / **1889** | **249ms** / 1788 |
| `Thanks` | 否 | 395ms / **119** | **290ms** / 4723 |

## 4. 分析

### 4.1 Token：判断省 58%

| 指标 | 有判断 | 总是检索 | 差异 |
|---|---|---|---|
| 输入均值 | 1019 | 2453 | **-58.5%** |
| 输入中位 | 1004 | 1817 | -44.7% |
| 输出均值 | 80 | 79 | 持平 |

省下的仍是"检索到的 8 段资料"及其拼装。`Thanks` 最典型：
判断方案 119 token，总是检索 **4723 token**（39.7 倍）。

### 4.2 首字：判断反而更慢

- **中位 357ms vs 259ms**，判断慢 98ms；
- **P95 500ms vs 400ms**，尾部也更差。

原因很直接：移除正则快路径后，**寒暄和致谢也要先过一次 router**（约 300~400ms），
而这类问题本来可以立刻回答。省下的检索时间（约 200~300ms）不足以抵消 router 的开销。

分问题看得很清楚：

| 问题类型 | 有判断是否占优 | 说明 |
|---|---|---|
| 寒暄 `Hello` | 是（263 vs 360ms） | 跳过检索省的时间 > router 开销 |
| 致谢 `Thanks` | 否（395 vs 290ms） | 恰好相反 |
| 必检索问题 | 否（316 vs 193ms） | router 固定开销叠加在检索之前 |
| 历史追问 | 否（474 vs 249ms） | router 开销 + **误判**双重损失 |

### 4.3 调用次数：判断每轮多一次

| 方案 | LLM 调用/轮 |
|---|---|
| 有判断 | **2.0** |
| 总是检索 | 1.0 |

判断方案 = router 1 次 + 生成 1 次；总是检索 = 生成 1 次。

### 4.4 两种失败模式的代价

| 失败 | 后果 |
|---|---|
| 有判断 **误判为需检索**（历史问题 4/4） | 多约 1770 token、首字 474ms（本应 ~250ms） |
| 总是检索 **不该查却查了**（寒暄/致谢） | 多 1336~4604 token、首字 290~360ms |

## 5. 结论

1. **判断的价值已从"更快"变成"更省"**：输入 token 降 58%，
   但首字中位反而慢 98ms（357ms vs 259ms）。
2. **原因是寒暄不再有特判**：每次判断都要付一次 router 调用（约 300~400ms），
   这是判断方案的固定成本，与是否真的检索无关。
3. **按目标二选一**：
   - 追求**最低首字延迟** → 总是检索（259ms），代价是 token 涨到 2.4 倍；
   - 追求**成本可控** → 保留判断，但要接受每轮多一次调用与约 0.1s 的首字代价。
4. **误判仍是最大风险**：历史追问 4/4 被误判为需检索，把"秒回"变成"完整检索"。
   优化方向是提升 router 准确率（换更强模型 / 加规则），而不是取消判断。
5. **如果想两全**：可以对"明显无需检索"的输入做**更轻量**的拦截（比如更小的分类模型或关键词规则），
   把 router 的成本压到几十毫秒——但这属于重新引入特判，需权衡维护成本。

## 6. 复现

```bash
uv run python tests/compare_router_decision.py --repeat 6 --token-repeat 4
```

## 7. 局限

- 仅 4 个问题，覆盖寒暄/必检索/历史/致谢各一，样本小，方向性结论为主。
- 单机本地服务，token 与延迟绝对值受硬件影响，看相对差异。
- 首字与 token 分两阶段测量（流式无 usage），两者不是同一次运行的样本。
- 输入 token 方差大（受检索到的文档长度影响），故同时给出均值与中位。
