# 检索后排序方案对比：无排序 / rerank / RRF

## 1. 目的

召回之后怎么排序，直接决定进入上下文的几段资料对不对。本报告在**同一召回池**下横评三种方案：

| 方案 | 做法 | 额外开销 |
|---|---|---|
| **无排序** | 沿用召回顺序（bm25 在前、向量补位），不作处理 | 0 |
| **rerank** | cross-encoder（`bge-reranker-v2-m3`）对候选池重新打分 | 数百毫秒 |
| **RRF** | 按名次倒数融合两路结果（`rrf_k=20`） | 微秒级 |

## 2. 方法

脚本：`tests/compare_ranking.py`

```bash
uv run python tests/compare_ranking.py --repeat 2
```

- 召回池固定：`bm25_k=25` + `sem_k=15`，按 `(来源, 文本)` 去重；
- 三个方案共用同一候选池，**只改排序方式**，保证可比；
- 排序结果按**文档去重**后截断（同一文档多个分块不重复占位）；
- 指标：`Recall@topN`、`MRR`（正解首次出现名次的倒数均值）；
- 耗时：rerank 实测（重复 2 次取中位），RRF 只计融合本身，无排序为 0。

评测集：`data/eval/queries.json`，两档各 30 条：

| 档位 | 构造方式 |
|---|---|
| `title` | 文档 H1 标题当查询（简单，有字面重合） |
| `paraphrase` | 本地模型生成的英文口语问题（困难，无字面重合） |

## 3. 结果

### 3.1 标题档（30 条）

| topN | 无排序 Recall / MRR | rerank Recall / MRR | RRF Recall / MRR |
|---|---|---|---|
| 5 | 86.7% / 0.631 | **100.0% / 0.940** | **100.0%** / 0.762 |
| 8 | 100.0% / 0.651 | **100.0% / 0.940** | 100.0% / 0.762 |
| 10 | 100.0% / 0.651 | **100.0% / 0.940** | 100.0% / 0.762 |

耗时：无排序 0ms ｜ rerank **752ms** ｜ RRF **0.01ms**

### 3.2 改写档（30 条）

| topN | 无排序 Recall / MRR | rerank Recall / MRR | RRF Recall / MRR |
|---|---|---|---|
| 5 | 70.0% / 0.548 | 80.0% / 0.696 | **90.0% / 0.723** |
| 8 | 83.3% / 0.568 | 86.7% / 0.704 | **90.0% / 0.723** |
| 10 | 90.0% / 0.575 | **93.3%** / 0.711 | 90.0% / **0.723** |

耗时：无排序 0ms ｜ rerank **810ms** ｜ RRF **0.02ms**

### 3.3 端到端首字延迟（TTFT）

排序只占整轮问答的一小段，但直接体现在用户"多久看到第一个字"。

脚本：`tests/compare_ranking_e2e.py`。同一张图只切换 `ranking`，2 个必检索问题 × 3 轮，
每轮轮转执行顺序以抵消先后偏差；只统计 **chatbot 节点**吐出的首个 token（避免把 router 的 chunk 当首字）。

| 方案 | 首字平均 | 首字中位 | 最快 | 最慢 | 总耗时中位 |
|---|---|---|---|---|---|
| 无排序 | 623ms | 619ms | 580ms | 657ms | 7.2s |
| **rerank** | **1682ms** | 1677ms | 1615ms | 1770ms | 7.3s |
| **RRF** | **615ms** | 614ms | 598ms | 642ms | 7.5s |

- **rerank 让用户多等约 1.06s**（1682ms vs 623ms），与它 800ms 的重排开销基本吻合；
- **RRF 与"无排序"几乎一致**（615ms vs 623ms），融合成本可忽略；
- 三者总耗时相近（7.2~7.5s），因为生成阶段占了大头，排序差异被稀释。

## 4. 分析

1. **无排序明显不够**：改写档 top-5 只有 70.0%，比 RRF 低 20 个百分点。
   原因是它把 bm25 结果无条件排在前面，而 bm25 对口语问题本就弱。
2. **rerank 的优势在"排序质量"，不在"召回"**：
   标题档三种方案召回都到顶，但 rerank 的 MRR 是 **0.940**，比 RRF 高 0.178、
   比无排序高 0.289——它把正解压到第 1 名的能力最强。
3. **RRF 的优势在"口语问题 + 小 topN"**：
   改写档 top-5 召回 90.0%（rerank 80.0%、无排序 70.0%），MRR 也最高（0.723）。
   而且融合开销只有 0.02ms，比 rerank 便宜 4 个数量级。
4. **topN 放大到 10 后 rerank 追回召回**（93.3% vs 90.0%，+3.3pt），
   但 MRR 仍低于 RRF（0.711 vs 0.723），代价是 810ms 和更长的上下文。
5. **首字延迟上，rerank 的代价是双倍的**：不仅召回/MRR 没有优势，
   用户还要多等 1.06s（1682ms vs 623ms）；RRF 则与不排序无异（615ms）。

## 5. 选型建议

| 场景 | 推荐 | 理由 |
|---|---|---|
| 用户习惯直接搜术语（标题式查询） | **rerank** | MRR 0.940，让最相关的那条排第 1；召回已满，拼的是排序 |
| 用户口语化提问（真实客服场景） | **RRF** | top-5 召回 90%、MRR 0.723，成本≈0 |
| 延迟敏感 / 高并发 | **RRF** | 首字 615ms 对 rerank 的 1682ms |
| 需要"最相关一条必须排第一" | **rerank + topN≥8** | 排序精度最高，接受 800ms |

**组合思路**：默认走 RRF（免费、口语问题更强），只有在需要精排或能承担延迟时叠加 rerank。

## 6. 局限

- 每档仅 30 条查询，约 ±3 个百分点噪声；MRR 差异看趋势。
- 正解按「文档」判定，不区分钟级命中位置。
- 语料为英文技术文档，中文提问会使 bm25 失效（见《英文Query测试报告》的勘误说明）。
- rerank 耗时依赖本地服务，绝对值仅供量级参考。
