# RAG 两种实现：固定编排 vs Agentic

## 目标

同一套语料、同一个模型，对比两条 RAG 路线：

| | 流程控制 | 构建函数 |
|---|---|---|
| **A** | 固定编排，router 节点决定是否检索 | `rag.workflow.build_graph(...)` |
| **B** | `create_agent` + 检索工具，模型自主决定 | `rag.agentic.build_agent(...)` |

两者的检索链路完全一致：**bm25(10) + 语义(15) 去重 → rerank 取前 5**。
区别只在于「要不要检索」这一决策由谁做、以及流程是否写死。

## 实现差异

### A. 固定编排（`src/taste_rag/rag/workflow.py`，默认 `ranking="rerank"`）

```mermaid
graph TD
    Start([Start]) --> Summarize[summarize]
    Summarize --> Router{Router<br/>判是否检索}
    Router -- 检索 --> BM25[bm25 10]
    Router -- 检索 --> Semantic[semantic 15]
    Router -- 不检索 --> Chatbot
    BM25 --> Rank[去重 + rerank 取 5]
    Semantic --> Rank
    Rank --> Chatbot[chatbot]
    Chatbot --> END([END])
```

- 是否检索由 **router 节点**单独调一次模型判定（`with_structured_output` 返回 `retrieve/chatbot`）。
- 检索固定只做**一次**，字段 `context` 传给 chatbot。

### B. Agentic（`src/taste_rag/rag/agentic.py`）

```mermaid
graph TD
    Start([Start]) --> Agent[agent<br/>create_agent]
    Agent -- 调用 search_knowledge_base --> Tool[检索工具<br/>bm25+语义 -> rerank]
    Tool --> Agent
    Agent -- 不调用 --> END([END])
```

- 只提供一个工具，**何时检索、检索几次、要不要换关键词再查**都由模型决定。
- 提示词承担了原来 router 的职责，是这条路线成败的关键：

```text
【什么时候调用工具 search_knowledge_base】
- 问题涉及 LangChain、LangGraph 的概念、API、类名、参数、配置方式时，先调用它，不要凭记忆作答。
- 一次检索结果不相关或信息不全时，换更准确的关键词再检索，最多 3 次。
- 寒暄、与文档无关的闲聊、或对话历史里已经给出过答案时，不要调用工具，直接回答。

【怎么回答】
- 只使用工具返回的资料和对话历史，不要补充资料之外的内容。
- 资料里没有的信息，直接说明「资料中没有提到」，不要编造。
- 用中文简洁回答，必要时给出代码片段，并标注来源文件名。
```

工具本身（两路召回后去重、重排）：

```python
@tool
def search_knowledge_base(query: str) -> str:
    """在 LangChain / LangGraph 官方文档库中检索，返回最相关的几段原文。"""
    candidates = dedupe([
        bm25_candidates(bm25, chunks, query, BM25_K),
        sem_candidates(retriever, query),
    ])
    # 去重 -> rerank 取前 5
```

## 测试

脚本：`tests/compare_rag.py`

```bash
uv run python tests/compare_rag.py
```

**串行**执行：A 跑完 6 轮，B 再跑一遍；各自独立的 `thread_id` 与内存 checkpointer。

### 语料（6 轮，英文）

语料是英文文档，提问也必须用英文，否则测到的是语种不匹配而不是检索能力。

| 轮次 | 输入 | 期望检索 | 考察点 |
|---|---|---|---|
| 1 | `Hello` | 否 | 寒暄不检索 |
| 2 | `How do I define a tool in LangChain?` | 是 | 需要查文档 |
| 3 | `What is the basic flow of vector store retrieval?` | 是 | 需要查文档 |
| 4 | `What technical question did I just ask?` | 否 | 历史可回答 |
| 5 | `Thanks` | 否 | 致谢不检索 |
| 6 | `How do I define a tool in LangChain?`（重复第 2 轮） | 否 | 历史已有答案 |

### 检索链路基准（两档评测集）

脚本与数据：

```bash
# 1) 生成评测集：30 篇文档 → 标题档 + 改写档，共 60 条
uv run python tests/build_eval_set.py --docs 30

# 2) 分别跑两档
uv run python tests/benchmark_retrieval.py --eval-set data/eval/queries.json --tier title
uv run python tests/benchmark_retrieval.py --eval-set data/eval/queries.json --tier paraphrase
```

**评测集设计**（`data/eval/queries.json`，`seed=42`，可复现）

| 档位 | 构造方式 | 难度 |
|---|---|---|
| `title` | 文档 H1 标题当查询，正解为该文档 | 简单，与原文有字面重合 |
| `paraphrase` | 本地模型读「标题 + 中段内容」生成**英文口语问题**，正解仍是该文档 | 困难，与原文无字面重合 |

> 语料是英文文档，查询也必须用英文：跨语种（中文问英文库）测的是语言不匹配，不是检索能力。

每条查询重复 3 次，每档 30 条 → 90 次采样。

**指标口径**

- `Recall@K`：正解文档是否进入该阶段 top-K（按文件路径判断）
- `MRR`：正解首次出现名次的倒数均值（1/rank），衡量排序质量，而不只看"有没有进前 K"
- `候选池`：bm25 ∪ 向量的并集，即 **rerank 的理论上限**
- `不重排 top5`：直接取候选池前 5（bm25 在前、向量补位）——**这会偏向 bm25，偏悲观**
- `RRF top5`：只按名次做倒数排名融合，不花模型成本，是**公平的无重排基线**
- `重排保真度`：`rerank 命中 / 候选池命中`

**标题档（简单）**

| 阶段 | 平均 | 中位 | P95 | Recall | MRR |
|---|---|---|---|---|---|
| bm25 top10 | 0.5ms | 0.5ms | 0.7ms | 96.7% | 0.625 |
| 向量 top15 | 12.2ms | 11.0ms | 17.1ms | 96.7% | 0.719 |
| 候选池 | — | — | — | **100%** | 0.626 |
| 不重排 top5 | — | — | — | 83.3% | 0.609 |
| RRF top5 | — | — | — | 96.7% | 0.786 |
| rerank top5 | **505.0ms** | 501.6ms | 582.9ms | 96.7% | **0.911** |

**改写档（困难，英文口语问题）**

| 阶段 | 平均 | 中位 | P95 | Recall | MRR |
|---|---|---|---|---|---|
| bm25 top10 | 0.5ms | 0.5ms | 0.7ms | 83.3% | 0.553 |
| 向量 top15 | 14.8ms | 13.8ms | 23.3ms | **90.0%** | 0.679 |
| 候选池 | — | — | — | **93.3%** | 0.560 |
| 不重排 top5 | — | — | — | 63.3% | 0.528 |
| RRF top5 | — | — | — | **83.3%** | **0.698** |
| rerank top5 | 565.9ms | 565.2ms | 659.8ms | 76.7% | 0.681 |
| rerank 去重 top5 | — | — | — | 80.0% | 0.696 |

**top-k 消融（改写档）** —— 对比免费融合与付费重排

| top-k | RRF 召回 / MRR | rerank 召回 / MRR | rerank 去重 召回 / MRR |
|---|---|---|---|
| 5 | 83.3% / 0.698 | 76.7% / 0.681 | 80.0% / 0.696 |
| 8 | 90.0% / 0.709 | 80.0% / 0.686 | 90.0% / 0.709 |
| 10 | 90.0% / 0.709 | 83.3% / 0.689 | **93.3% / 0.713** |

**结论**

1. **语言必须匹配**：早先用中文问题测英文语料，bm25 掉到 26.7%——那测的是语种不匹配，不是检索能力。
   改成英文改写问题后 bm25 回到 83.3%，才是真实水平。
2. **简单档掩盖差异**：标题档下 bm25 / 向量 / rerank 全是 96.7%，只有 MRR 能看出排序差别；
   英文改写档才分得开：bm25 83.3% / 向量 90.0% / 候选池 93.3%。
3. **两路召回必须融合，不能顺序优先**：不重排基线（bm25 在前）只有 63.3%，
   同样候选池用 RRF 免费就能到 83.3%。
4. **rerank 的净收益有限**：top-5 时 rerank 76.7% **低于** RRF 83.3%；
   按文档去重也只到 80.0%；要到 top-10 且去重才反超（93.3% vs 90.0%，MRR 0.713 vs 0.709），
   代价是 566ms 与更长的生成上下文。
5. **同一文档的多个分块会挤占名额**：去重让 top-8 从 80.0% 提到 90.0%（+10 个百分点），这是免费改进。
6. **rerank 成本在候选池、不在输出条数**：top-5 → top-10 只多 35ms，可以放心提高 top-k。
7. **评测局限**：查询由本地 4B 模型生成、正解按「文档」而非「片段」判定、样本 30 条（约 ±3 个百分点噪声）。
   绝对数值不宜外推，但**同一链路不同配置的相对比较**可靠。

## 结论

1. **检索决策：A 稳定 5/6，B 5~6/6，失败模式不同**：
   A 每次都把第 4 轮「我刚才问过什么」误判成需要检索；
   B 大多能跳过，但在第 4 次运行中**漏检索**了第 2 轮 `How do I define a tool in LangChain?`（明确该查文档的没查）。
   一个偏向多查，一个偏向漏查，都不是稳定正确。
2. **耗时：英文语料下 B 慢约一倍**：A 稳定 17~19s，B 29~37s。
   差距集中在第 2、3 轮：B 需要额外一次模型调用决定是否用工具，且回答更长
   （第 3 轮 12.5~14.8s vs A 6.5~7.0s）。
3. **早前的中文数据作废**：中文提问时 A/B 都在 15~24s、B 一度更快；
   换成英文后差异才显现。那组数据受语种污染，不能用于比较两条实现。
4. **可控性与成本**：
   - A 多一次固定 router 调用（`max_tokens=128`，约 2s），流程确定、易调试、行为可预测；
   - B 的决策调用没有 token 上限，可能先写一段再调工具，耗时与行为都不固定。
5. **rerank 是耗时大头，但收益需重新评估**：单次检索 566ms 里约 99% 是 rerank；
   曾把两路召回改成并发，实测只省 0.6ms，收益可忽略，因此改回顺序调用。
   而英文改写档显示，top-5 下 rerank 相对免费 RRF 的净收益是**负的**（76.7% vs 83.3%）；
   若要保留 rerank，应配合「按文档去重 + top-k=10」（93.3%）。
   建议下一步做端到端答案质量对比（RRF vs rerank）再定去留。

## 选择建议

- 若问题形态稳定、要求行为可预测（客服常见场景）→ **A 固定编排**。
- 若问题类型差异大、需要多轮改写检索或按需多次查证 → **B Agentic**。
- 两者检索链路相同，可以先上 A 保底，再用 B 处理复杂问题（路由分发）。
